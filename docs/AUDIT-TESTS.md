## Method, and how far to trust it

For each cluster of behaviour I introduced one small semantic mutation into production code, ran that package's own vitest suite, recorded pass/fail, and restored the file with `git checkout --` (verifying byte-identical restore before continuing). 149 mutants across 7 workspaces.

**Node version.** `pnpm -w test` must run on Node 20.19.0. A bare `nvm use` from outside the repo silently selects **v26.0.0**, which breaks `better-sqlite3` — and only *some* packages fail, so the result still looks like a partial green. My first `carpool-tracker` batch was run that way and produced **20 false KILLs**: all 12 `index.test.ts` tests failed identically under every mutant, including a mutant that only changed an unrelated constant. I discarded that batch and re-ran everything with `cd <pkg>` *before* `nvm use` plus a hard `node -v == v20.19.0` assertion. Every result below is from a version-asserted run. This trap is worth a CI guard.

**Concurrency caveat (important).** Other audit agents were editing this same working tree while I ran. My evidence that a given result is trustworthy is that **every SURVIVED mutant reported the exact full clean-baseline count** for its package (core 56, tracker 46, hedera-x402 72 tracked, registry 108 tracked, mcp 50, dashboard 128, bench 46). A concurrent production edit would have shown up as a failure or a changed total. `git status --porcelain` and `git diff -- apps packages` were clean at every batch boundary. On that basis I vouch for all 49 survivors below; none is marked unverified. My own mutations were transient by design and were each restored within one test run — if the money-path audit saw four of them mid-run (`settler.ts:331`, `gate.ts:161`, `splitSale`, `derive.ts`), those were mine and their results, not mine, are the ones needing re-verification.

**Suite composition.** Three `audit-*.test.ts` files from the parallel audits appeared in the tree mid-run and add 120 tests. I excluded them from every run by passing the explicit `git ls-files` list of tracked test files, so the numbers below describe the 506-test suite as briefed, not the enlarged one.

## Defeating `apps/dashboard/lib/fixtures-unreachable.test.ts`

**Yes. It can be routed around trivially, and the bypass typechecks with zero errors.**

The guard is a literal substring scan: it walks `app/`, `components/` and `lib/`, reads each `.ts`/`.tsx` file, and checks `src.includes("fixtures.testonly")`. That gives it three independent holes — the directory list, the extension list, and the assumption that the import specifier appears verbatim in source.

**Attack A — re-export through an unscanned directory (verified).**
```
apps/dashboard/demoData/seed.ts:   export * from "../lib/fixtures.testonly.js";
apps/dashboard/app/page.tsx:       import { fixtureState } from "../demoData/seed";
```
`demoData/` is not in `APP_DIRS` and is not `lib/`, so nothing reads it. `app/page.tsx` contains no matching substring. Result: `fixtures-unreachable.test.ts` — **2 passed**, and `npx tsc --noEmit` exits **0**, proving the import genuinely resolves and the fixture types are live inside `app/`. Fabricated rows now reach the rendered app with the guard fully green.

**Attack B — split string literal in a dynamic import (verified).**
```
apps/dashboard/app/page.tsx:
  const SEED = "@/lib/fixtures" + ".testonly";
  export async function loadSeed() { return (await import(SEED)).fixtureState(); }
```
The contiguous substring never exists in the file. Result: **2 passed**.

Both attacks were reverted; `git diff` is clean.

**Further holes I did not need to exercise:** `walk()` filters on `/\.(ts|tsx)$/`, so a `.js`/`.mjs`/`.jsx` file under `app/` is never read even though `tsconfig` sets `allowJs: true` and Next.js compiles it; and a `paths` alias in `tsconfig.json` (e.g. `"@seed/*": ["lib/fixtures.testonly"]`) would let even a static import in `app/` avoid the substring.

**Recommended fix:** stop scanning text. Resolve the real module graph — walk imports transitively from the Next entrypoints (or assert on the built `.next` output), or move the fixtures out of the app's resolvable scope entirely (a separate package that is a `devDependency` of the test target only, so an import from `app/` fails to resolve rather than failing a grep). At minimum the current test should walk *every* directory except `node_modules`/`.next`, cover `.js`/`.jsx`/`.mjs`, and match on the resolved specifier rather than a raw substring — but a regex guard will always be one indirection behind.

### Fixed — module-graph walk, 2026-09-12

The recommended repair shipped. `apps/dashboard/lib/fixtures-unreachable.test.ts`
now enumerates the files Next.js actually renders (`app/**/{page,layout,route,…}`
plus root `middleware`/`instrumentation`, by Next's own file conventions),
resolves every import edge that survives compilation, and fails if a module
matching a test-only naming convention is reachable at **any** depth. Resolution
is **TypeScript's own** — `ts.createSourceFile` for the import scan and
`ts.resolveModuleName` against the options parsed from `tsconfig.json`, so `paths`
aliases are resolved by the compiler rather than approximated. No bundler, no new
dependency (`typescript` is already a devDependency here), 20 assertions in ~36 ms.

Design points that matter to a reader deciding whether to trust it:

- **Edges followed:** `import`, side-effect `import`, `export … from`,
  `export * from`, `export * as ns from`, `import x = require(…)`, dynamic
  `import(…)`, `require(…)`. **Not** followed: `import type` / `export type`,
  which are erased before a bundle exists and so cannot deliver a number to a
  page — and one of them (`lib/api.ts`'s type import of the registry's ledger) is
  load-bearing. The original grep assertions are **kept** alongside the walk, so a
  type-only or comment-level mention of the fixtures under `app/`/`components/` is
  still red.
- **A dynamic `import()`/`require()` with a non-literal argument is a hard
  failure**, not a skip. Attack B's split literal is unresolvable, and
  "unresolvable" must not read as "clean". Any unresolved relative or aliased
  specifier fails the same way.
- **The convention is enforced, not documented:** `*.testonly.*`, `*.test.*`,
  `*.spec.*`, `*.fixture(s).*`, `*.mock(s).*`, and any path segment
  `__tests__`/`__mocks__`/`__fixtures__`/`testing`/`fixtures`. Renaming the
  fixtures file does not escape the guard, and a *new* fixtures file is covered
  the day it is written.
- **The walk cannot be quietly emptied:** one assertion pins the discovered entry
  points, because a guard that walks nothing passes everything.

**Re-attacked, and it bites.** Each bypass was rebuilt in the real tree and both
guards run against it. `OLD` is the grep guard as it stood at the head of this
branch; `NEW` is the module-graph walk.

| clean tree | pass | pass |

The NEW failures name the chain, e.g. `app/page.tsx --[import
"../components/SwarmTable"]--> components/SwarmTable.tsx --[import "../data/a"]-->
data/a.ts --[export-from "./b"]--> data/b.ts --[export-from

- No `it.skip`, `describe.skip`, `it.todo` or `.only` anywhere in the tracked suite. No test file lacks `expect()`.
- **One conditional skip that silently shrinks the suite:** `apps/bench/src/ab-run.test.ts:102` is `describe.skipIf(!artifactPresent)`, where `artifactPresent` tests for a file **outside the repository** (on this machine, `~/Documents/RandomClaudeSessions/ethonline2026/ETHOnline-2026-research.md`). With the file present the suite is 46 tests; with `CARPOOL_AB_ARTIFACT` pointed anywhere else it reports `42 passed | 4 skipped` and **still exits 0**. So 4 of the 506 are machine-dependent, would vanish in CI or on any other clone, and their absence is a `console.warn` rather than a failure. The A/B measurement claim rests on those 4.

## Structural gaps found by static review (verified by reading, not by mutation)

A read-only pass over all 40 tracked test files turned up three structural findings I then confirmed directly. These explain several of the survivors above.

### `gate.test.ts`'s fake facilitator never implements `/settle` — the whole success path is unreachable

`packages/hedera-x402/src/gate.test.ts` stands up an Express fake facilitator with **exactly one route handler**, which unconditionally returns `{ isValid: false, invalidReason: "stub facilitator" }` (`gate.test.ts:52`). There is no `/settle` route at all. So `PaymentGate.handle()` can never get past its `verify` check in this file, and **every line after it is dead in test** — which is precisely why `hx-31` (drop the `!s.success` check), `hx-32` (`payer ?? "unknown"`), `hx-34` (`paid: 0`) and `hx-37` (silence the `LEDGER WRITE LOST` alarm) all survived. Four survivors, one root cause.

The file's own docstring (`gate.test.ts:16`) claims it is "the only test in the repo that exercised verify/settle". It exercises *verify's failure branch* and nothing else. `paidCtx` is assigned and never asserted. Note the unpaid/replay-lookup path genuinely *is* covered — `hx-30`, `hx-33` and `hx-35` all died — so the gap is specifically everything downstream of a successful settlement. Adding a `/settle` route plus a success-path assertion to that fake would close four of this audit's fifteen `hedera-x402` survivors in one change, and is the single highest-leverage test to write in the repo.

### `anchor.test.ts`: two of its five tests never call `anchorEpoch`

All five tests sit under `describe("anchorEpoch", ...)`. Three call it, but only its three *skip* branches (`empty`, `no-topic`, `no-client`). The remaining two (`anchor.test.ts:29` and `:35`) call only `merkleRoot()` — `anchorEpoch` is not in their path despite the describe block's name. So `anchorEpoch`'s `anchored: true` branch (the real HCS submission) has no coverage *in this package*. It is covered one layer up — `apps/registry/src/settlement.test.ts` asserts the real root through the harness's fake Hedera client, which is what killed `reg-19` and `reg-20` — so this is a misleading test-file boundary rather than an unguarded behaviour. `anchor.test.ts:37`'s `expect(() => merkleRoot([manifest])).not.toThrow()` is also redundant with the hex-shape assertion on the next line.

### `ledger.test.ts:429` pins a column nothing ever writes

`expect(buyerPeer.refundsIssued).toBe(0)` is unconditionally true: `refundsIssued` is threaded through `bumpPeer`'s signature (`ledger.ts:713,724,735`) and defined in the schema (`db/schema.ts:63`), but **no caller anywhere passes it** — `refundPurchase` bumps only `refundsReceived`. The assertion cannot fail for any behaviour of the system.

### On `apps/bench`'s stand-in — sharper than my note above

`localRegistry.publish()` is a plain method that injects straight into a `Map`: **no `authorSig` verification, no `magnetOf` recomputation, no `bodyHash` check, no `questionNorm` duplicate check** — all four of which the real `POST /publish` enforces (`server.ts:351,363-427`). Its `quote()` returns the test's hardcoded `priceNow` statically rather than computing through `priceAt()`/decay. `agent.test.ts` and `load.test.ts` — the bulk of bench's integration coverage — run only against this, so bench never exercises signature verification or dynamic pricing at all. My earlier note that the stand-in "cannot hide the `authorSig` class of defect" is correct only in the narrow sense that it has no publish *route*; the broader point is that bench's buyer is never tested against a registry that checks anything.

### One more real-embedder gap

`hashedEmbedder()` is an honest, well-labelled FNV-1a bag-of-words stand-in, and `search.test.ts`'s fixtures are vocabulary-disjoint — so a bag-of-words hash separates them trivially. That validates the plumbing (query → vector → index → threshold → ranking) correctly, but **nothing in the repo exercises the real ONNX MiniLM embedder on genuine semantic near-misses** (synonyms, paraphrases). A swapped or corrupted model checkpoint in production would be caught by no test here. Relatedly, `Embedder` is declared twice — `packages/carpool-tracker/src/embed.ts:25-29` and `apps/registry/src/embedder.ts:31-35` — textually identical, separately maintained, with no shared import, so nothing in the type system catches drift between them.

### Weak assertions worth fixing (highest-value only)

The static pass listed ~60 `toBeDefined`/`typeof`/`not.toThrow`/inequality assertions. Most are harmless guards next to real checks. These are the ones where a concrete value was available and unused:

- `apps/registry/src/reads.test.ts:97-99` — under a describe block titled "what an author was actually paid", the royalty **amount** is never asserted, only `typeof`. `paid − trackerFee = 500` was directly computable.
- `apps/registry/src/server.test.ts:155-156` — asserts `typeof body.embedding.dim`; the test set `EMBEDDING_MODEL`/`EMBEDDING_DIM` itself moments earlier.
- `apps/registry/src/server.test.ts:291` and `:480` — `typeof mine.health` / `typeof m.priceNow`, where both are deterministic (`0.4`, `110_000`) and `ledger.test.ts:346,351` proves the exact-value style is available for the identical shapes.
- `apps/dashboard/lib/format.test.ts:44` — `not.toThrow()` is the **only** assertion in "fmtTime accepts unix seconds"; the returned string is never inspected. (Consistent with `format.ts` being the least-tested module in the repo — see the `CENT`/`fmtCent`/`pct`/`shortId` survivors.)
- `apps/mcp/src/e2e.test.ts:223-229` — four `typeof` checks on `.well-known` fields with no value assertion anywhere in the file, even though the harness's configured values are known.
- `packages/carpool-core/src/manifest.test.ts:45,50,54,59` — unmatched `toThrow()` for "rejects a zero half-life" etc.; passes on a throw for *any* reason. `manifest.test.ts:62-70` shows the matched form was available.
- `apps/bench/src/agent.test.ts:46` — `expect(line.latencyMs).toBeGreaterThanOrEqual(0)` is tautological; `Date.now() - start` can never be negative.
- `apps/registry/src/ledger.test.ts:578-579` — seven concrete `[paid, fee]` pairs whose exact split is fully determined, checked only by inequality.

### Two more name overclaims

- `apps/bench/src/load.test.ts:63-65` — "throws on a non-ok response instead of returning an empty catalog silently" actually only produces a connection-refused error before any HTTP response exists; the real `if (!res.ok) throw` branch (`load.ts:62`) never executes.
- `apps/registry/src/delist.test.ts:150-156` — "keeps every row: the artifact, its body hash and its **manifest hash** are all still there"; the `manifestHash` column is never read or asserted.

### A methodological correction to the static pass

Its "would survive a constant stub" list evaluated tests **individually rather than against the whole suite**, and so overstates the case in several places. Where its conclusions conflict with my executed mutations, the mutations govern: `freshness`, `isExpired`, `health`, `canonicalHash`/`magnetOf` and `hookOutput` are all reported there as stub-survivable, but stubbing or mutating each of them **does** fail the suite (`core-02` killed 5 tests, `core-05`/`core-06` killed `isExpired` tests, `core-07`–`core-10` killed `health` tests, `core-16`/`core-17`/`core-20` killed magnet tests, `mcp-06` killed 8 consent tests). Individual weak tests exist within those files; the functions themselves are constrained. The entries that *are* genuine — because the function really has no stronger test — are `fmtTime`, `assertSeconds`, `findSeeder`, `TrackerIndex.remove`, `findDuplicateQuestion`, and `RegistrySearch.unindexArtifact`/`backfill`. The last two independently corroborate my executed survivors `reg-29` and `reg-26`.

## The tests that are genuinely well built

Three claims were checked by reverting the real fix and confirming the test actually fails. All three hold:

| Test | Fix reverted | Result |
|---|---|---|
| `packages/hedera-x402/src/settler.test.ts` — failure classification (defect I1) | `reconcile` treats a mirror-node record as proof of payment (`matches.find(success)` → `matches[0]`) | **6 tests fail.** Genuinely falsification-verified |
| `apps/registry/src/search.test.ts:103` — "ranks the matching artifact first even though it is the OLDEST in the corpus" | `query()` returns pre-Phase-C behaviour: every live artifact, newest-first, ranking ignored | **6 tests fail**, including that one by name |
| `apps/mcp/src/e2e.test.ts` — the C2 wire-shape suite | `carpool_publish` sends `signature` instead of `authorSig` | **10 of 14 fail.** It catches the bug precisely because it runs against the real registry via `apps/registry/src/testing/harness.ts`, not a stand-in |

Also worth naming:
- **`apps/registry/src/settlement.test.ts`'s `EpochRunner` block.** Removing the single-flight guard at `settlement.ts:148` is caught by "two callers racing one epoch produce one anchor, not two" — and **not** by "two concurrent POST /settle calls produce one batch" at `settlement.test.ts:235`, which still passes with the bug present. The repo already documents this in the comment above the block; my mutation confirms it. That older HTTP-level test remains in the suite and remains evidence of nothing about concurrency. The fix — drive the shared object directly instead of two round trips — is the right pattern and should be the template for the `Settler.settle()` gap listed above.
- **`apps/mcp/src/consent.test.ts`** parameterises every rule over both `decideConsent` *and* the executed hook, which is exactly the repair for the "tested a different function than the one that runs" failure.
- **`apps/dashboard/lib/decay.test.ts:22`** reads core's source off disk to assert the duplicated `0.125` constant has not drifted — a cheap, honest guard against a cross-package constant it deliberately cannot import.
- **`apps/bench/src/ab-run.test.ts` and `apps/mcp/src/e2e.test.ts`** both boot the real registry via `harness.ts` with the deterministic `hashedEmbedder()`. Where a real component exists, these use it. `apps/bench/src/support/localRegistry.ts` remains the one hand-written stand-in, but it is narrower than it looks: it wraps the **real** `PaymentGate` and stubs only the facilitator plus two read routes, and it does not implement `POST /publish` — so the `signature`/`authorSig` class of defect cannot hide in it. The residual risk is drift in the `/search` and `/artifact/:magnet` response shapes it hand-rolls.
