# Swarm implementation plan — hostile review

*Reviewed 12 Sep 2026 against `docs/SWARM-IMPLEMENTATION.md`, `../../swarm/PIVOT-ANALYSIS.md`, `../../swarm/PLAN.md`, and the Carpool code as it sits on disk (`main` @ `22e6156`, tag `v0.1.0-reproducible`). Every code claim below was checked by reading the file named; every external claim was checked against a source, marked **[V]** verified or **[?]** unverified.*

---

## 1. Verdict

The plan is not buildable as written and the product is unlikely to work, for one structural reason and several mechanical ones. Structurally: Phase 0 — which the plan correctly says "gates everything" — cannot measure the quantity the market depends on. It harvests one person's Claude Code transcripts, which on this machine span 27 days (16 Aug–12 Sep; Claude Code deletes transcripts after 30 days by default), cover four active projects, and contain roughly 90 research-shaped turns out of 7,179 human turns. A collision rate measured there is a *self-repeat* rate for one author; the market needs a *cross-author* repeat rate, which no single-user corpus can estimate at all. Mechanically: the "45% reuse" figure dissolves on contact with the code. The x402 flow, quote binding and 402 emission live as closure-local internals of one 521-line `carpool()` Router function with no exports (`packages/carpool-express/src/index.ts`); the outbox's op type is `"pioneer" | "rider" | "refund_due"` (`outbox.ts:20`); `anchor.ts` calls `loadConfig()` which refuses to start without a `carpool.policy.json` containing exactly four DeFi query classes and anchors a Merkle root over *(payee, amount)* accruals, not manifest hashes. So "Phases 1–4 do not touch Carpool's packages" is true only if Phase 3 copy-pastes ~250 lines, which is what will actually happen and is fine — but it should be stated, because the plan's claimed safety property ("a refactor cannot destabilise a submitted project") is being bought with a fork, not a dependency. The data model has a primary-key collision that prevents two authors from ever publishing on the same question, no `scope` column despite `scope` being in the magnet, and a `peer` table that cannot compute anything the plan calls "health" or "ratio". The consent model is cited, not carried through: nothing in the repo layout implements the scanner, the MCP server provably cannot detect a subagent (anthropics/claude-code#32514, closed not-planned), and the corpus Phase 0 proposes to commit to `packages/swarm-tracker/bench/` is the author's own client-project questions — exactly the leak §8a exists to prevent. The payment stack it inherits is real (verified below), and the pricing argument is mostly right. Those are the parts to keep.

## 2. Fatal or near-fatal problems (ordered by severity)

### 2.1 Phase 0 measures the wrong population and cannot reach its own sample size

**What breaks.** §3 targets "150–300 questions across ≥3 months" and a collision-rate threshold of 10%. On this machine:

- `~/.claude/projects/` holds 25 transcripts in 4 projects with content (12 in `RandomClaudeSessions`, 7 `n9n-new-frontend`, 5 `Travel-App`, 1 `ashrafi`); 13 project directories are empty. Oldest transcript 2026-08-16, newest 2026-09-12. `cleanupPeriodDays` is unset, so Claude Code's default 30-day deletion applies — the corpus is structurally capped at one month, not three.
- A permissive regex over human turns (`research|investigate|compare|what is|how does|explain|evaluate|…`, length > 60) matches 94 of 7,179 turns, and sampling those shows most are task-notifications, skill loads and coding directives ("I dont like the latitude longitude lines"). The real count of research questions is plausibly 20–40.
- Even if 300 questions existed, the plan labels "~500 pairs … biased toward near-misses". 300 questions give 44,850 pairs; 500 hand labels are 1.1%, drawn non-uniformly. **Precision@1 computed on a near-miss-enriched sample is not the deployment P@1**, and a collision rate needs an unbiased denominator, which the plan's sampling explicitly avoids.
- Worst: collision within one person's history measures whether *Romario re-asks Romario's questions*. That is solved by local memory or a personal cache at zero price; it is not evidence that *a stranger* asked the same thing. The only external evidence the research turned up cuts the same way: Teevan et al. (SIGIR 2007) find ~40% of web queries are *same-user re-finding* [V]; the Stack Overflow duplicate literature (~53% of closed posts are duplicates [V]) is cross-user but measures short factual questions, not multi-hour research syntheses.
- The thresholds are invented. No derivation for 10% or 70% appears anywhere. A derivation is cheap: with margin `m` and a buyer who saves cost `C` on a hit and wastes `mC + reading time` on a miss, break-even P@1 ≈ `m/(1+m)` — around 33% at `m=0.5`, 41% at `m=0.7`. The 70% bar may be right for *trust* reasons ("two bad purchases") but that is a behavioural claim, not a number, and it contradicts §4.4 which says the tracker "can be imperfect" because the buyer judges from the manifest. Pick one: if the agent judges, Phase 0 must measure precision *after* agent judgement over the manifest, which it does not.
- "Effort: 1 day." Labelling 500 pairs at one careful minute each is 8 hours before harvesting, embedding, sweeping or writing the bench.

**Fix.** Phase 0 cannot be run from one laptop. Either (a) recruit ≥5 other Claude Code users to contribute anonymised research question lists (question text only, hand-redacted) and measure *cross-user* collision, or (b) substitute a public proxy corpus with real cross-user repetition — e.g. Stack Overflow "research-shaped" questions with their duplicate links as ground truth, or a set of published deep-research prompts — and be explicit that it is a proxy. Sample pairs uniformly for the collision rate; enrich near-misses *only* for the threshold sweep. Derive the go/no-go bar from the margin. Budget 3 days.

### 2.2 The magnet as primary key forbids competing artifacts and defines nothing

**What breaks.** `artifact.magnet TEXT PRIMARY KEY` where `magnet = sha256(canonical question ‖ scope)` (§5, §6 Phase 1).

- Two authors answering the same question collide on the primary key. The second `POST /publish` fails. A market with one seller per question is not a market; it is a first-mover lockout — and the first mover can be junk.
- Conversely, a plagiarist republishes a bought body under a question with one word changed and gets a fresh magnet at a lower price. Nothing in the plan detects near-duplicate *bodies* (a `body_hash` match only catches byte-identical copies).
- "Canonical question" is undefined. `policy.ts::canonical` sorts JSON keys; it says nothing about whitespace, case, punctuation or paraphrase in a natural-language string. Phase 1's acceptance test ("magnet stability across key orderings") tests the JSON property, not the string property, so it will pass while the magnet remains unstable across trivially different phrasings of one question.
- `scope` is in the hash but there is no `scope` column, so it can never be displayed, searched or verified.

**Fix.** Artifact id = `sha256(manifest)` (content-addressed, per-author, collision-free). Keep a *separate* `question_key` for grouping, derived from the embedding-cluster or a normalised string, non-unique. Add `scope TEXT`. Add a near-duplicate check on publish: reject or flag bodies whose embedding cosine to an existing body exceeds a threshold, and surface "N other artifacts answer this question" in search.

### 2.3 Reuse is a fork, not a dependency — and the plan's sequencing guarantee depends on that distinction

**What breaks.** §2 and §10 state that Phases 1–4 do not modify Carpool's packages; Phase 3 says "Reuse from Carpool: 402 flow, issued-quote binding, outbox, auth boundary." Reading `packages/carpool-express/src/index.ts`:

- The exports are `carpool`, `chooseRole`, `fetchWithRetry`, `LedgerClient`, `FileBodyStore`, `MemoryBodyStore`, `RefundOutbox`, `replayOutbox`, and types. `send402`, `buildRequirements`, `issuedKey`, the `issued` LRU, `ensureInit`, `owe` and the entire verify→settle sequence are closure-locals inside `carpool()` (lines ~170–520). They cannot be imported. The route is `router.get("/:cls")`, parses a `QueryClass`, calls `cacheKey`, calls `ledger.quote(key, cls, maxAge)`, branches on `role === "pioneer"` and calls `opts.upstream.fetch`. None of this applies to Swarm.
- `RefundOutbox`'s `OutboxOp = "pioneer" | "rider" | "refund_due"` and `replayOutbox` dispatches on exactly those three strings. Swarm's op is "purchase". Using it "unchanged" means either mislabelling purchases as riders or editing `outbox.ts` — i.e. touching `carpool-express`.
- `LedgerClient` posts to `/ledger/quote|pioneer|rider|refund-due` with Carpool's shapes. Unusable.
- `FileBodyStore` keys files by *lineage id*, `JSON.parse`s the whole body on read, and fronts a 10,000-entry LRU. For MB-sized artifacts that is up to 10 GB of resident memory. It is not content-addressed. Phase 3 correctly says "content-addressed files" — that is new code, not reuse.
- `apps/settlement/src/auth.ts` is in an *app*, not a package. `apps/swarm-registry` cannot depend on `@carpool/settlement` without either publishing the app as a workspace package (a Carpool change) or copying the 78 lines. The header name is `x-carpool-key` and the env var `LEDGER_API_KEY`.
- `settler.ts::settleEpochInner` reads `process.env.CARPOOL_PRIVATE_KEY`, is typed against Carpool's `Ledger` class (`ledger.unsettledAccruals()`, `createBatch`, `sumAccruals`, `markSettled`), and calls `anchorEpoch`. `anchor.ts` calls `loadConfig()` (`config.ts:60`) which throws without `carpool.policy.json`, then anchors `{batchTxIds, merkleRoot(allAccruals), lineageCount, consumerCount, policyHash}`. The Merkle root is over *payee:amount* leaves (`merkle.ts`) and is cumulative — the ledger DB confirms two consecutive anchors carrying the identical root `27e4e54d…`. Phase 4 wants "an anchor whose merkle root covers the epoch's manifest hashes". That is a different anchor with a different leaf type and different per-epoch semantics. `merkle.ts` (34 lines) is the only piece that transfers unchanged.
- `groupAndChunk` (pure, ~30 lines) transfers unchanged. `policy.ts::canonical` (12 lines) transfers. `sha256` (4 lines) transfers. `errors.ts` classifies *upstream* failures; Swarm has no upstream (the pivot analysis says so itself), so it is not reused at all.

Honest count of code that imports cleanly: `merkleRoot`, `groupAndChunk`, `canonical`, `sha256`, the `PaymentRequirements` construction pattern, and the four Hedera scripts (`associate`, `create-accounts`, `create-topic`, `distribute` — all four exist). Perhaps 150 lines plus the *knowledge* in `X402-RESEARCH.md`. The knowledge is genuinely valuable; the percentage is not 45%.

**Fix.** Say "fork, then extract." Phase 3 copies the relevant ~250 lines of `index.ts` into `apps/swarm-registry/src/x402.ts` with Swarm's shapes; Phase 5 diffs the two and extracts `x402-kit`. Drop the 45% figure. The sequencing guarantee survives because the copy does not touch Carpool — but say that is the reason.

### 2.4 The consent model is cited, not implemented, and part of it is unimplementable where the plan puts it

**What breaks.** Phase 6 lists the §8a rules and calls them "non-negotiable", then provides no component, no data flow and no acceptance test for any of them.

- **Subagent/hook/background detection.** §8a: "If Swarm runs inside a subagent, a background task, a scheduled run or a hook, `swarm_publish` is unavailable regardless of settings." Claude Code sends no agent-identity context to MCP servers; the request for it (anthropics/claude-code#32514) was closed "not planned" [V]. An MCP server cannot enforce this. It must be enforced client-side (a `PreToolUse` hook denying `mcp__swarm__swarm_publish` when `CLAUDE_AGENT_TYPE`/subagent context is present, or by simply not registering the tool in subagent MCP configs). The plan puts it in the server.
- **The "explicit yes".** MCP elicitation (spec 2025-06-18) is supported in Claude Code CLI as a blocking modal [V], but not in Desktop/claude.ai, and its behaviour inside `-p` and subagents is undocumented. Without elicitation, "explicit yes" means the model reads the diff, asks in chat, and the user types "yes" — consent mediated by the same LLM the rule is protecting against. The plan does not name elicitation.
- **The scanner.** "Detected secrets… file paths or code from a repo with no public remote… questions matching sensitive patterns (`our`, `internal`, client names, anything naming a private host)". Regex/entropy scanners (gitleaks, trufflehog, secretlint) catch key *shapes*; none catch client names or internal hostnames [V] — that is NER/PII territory. The plan lists this as a strip-not-warn gate and budgets it nowhere. It is not in `swarm-core`, `swarm-tracker` or `swarm-mcp`'s descriptions.
- **Per-project `off/ask/auto`.** Feasible: stdio MCP servers receive `CLAUDE_PROJECT_DIR` and `roots/list` [V]. But the plan does not say where the setting lives or how the server reads it.
- **Redaction / publish-with-edits.** Needs an editing surface. MCP tools return text; there is no diff UI. Unaddressed.
- **The plan violates §8a itself.** §3's deliverable puts "the corpus, labels" from the author's own transcripts into `packages/swarm-tracker/bench/` in a public repo. Those transcripts include LICET fee-portal infra, Asharfi proposals, client work. The one artefact the plan commits to shipping is a leak of exactly the class §8a says "ends the product."

**Fix.** Make consent Phase 1.5, with code: a `PreToolUse` hook shipped with the MCP config that denies `swarm_publish` outside the main interactive session; elicitation as the yes/no surface with a documented fallback of "refuse if elicitation unavailable"; `secretlint` (JS-native) for secrets plus a user-maintained never-publish word list for names/hosts, both *blocking*; a redaction round-trip test. Keep the Phase 0 corpus private — commit only the numbers and a synthetic/public bench.

### 2.5 The pricing anchor is fiction, and the decay-only model has a hole the plan does not name

**What holds.** The pivot analysis §1 argument is correct: Carpool's `P/n` splits a cost incurred *for* the buyers; Swarm's author bore cost before any buyer existed, so there is no bill to split and a capped royalty would be a rule for splitting a bill, not paying for work. Decay-only is a defensible starting point.

**What does not.**
- `P ≤ estimatedCostUsd × margin` is enforced against a number the author types in. It can be inflated by lying, and — more corrosively — by *honestly* running wasteful research (burn tokens on purpose, report the true bill). Cost is not value. The manifest's "this took Opus N seconds and $M" is a signal only if the buyer believes it, and there is no verification path: token counts are not in the body, and "a lie is checkable against the body after purchase" (PLAN.md §5.2) is false — you cannot recover input tokens from a synthesis.
- The good is static and copyable with zero marginal cost. Buyer 1 can republish a paraphrase as their own artifact (see 2.2). Nothing prevents it. Every information-goods marketplace hits this (Arrow's paradox [V]: you cannot value information until you have it, and once you have it you need not pay). PLAN.md §5 lists four trust mechanisms; the implementation plan keeps one (free manifest) and drops the other three (provenance verification, refund window, ratio-as-reputation) or implements them as dead columns.
- `floor` and `halfLifeDays` are author-set with no market feedback; an unsold artifact just decays to floor and sits there. No demand signal ever reaches the price. That is not necessarily wrong for v1, but the plan calls the price "anchored" and "legible", and it is neither.
- The pivot analysis's own point 3 undercuts its decay argument: "Buyer 1 and buyer 40 receive an identical file" — yes, and on day 38 buyer 1 *holds* a 38-day-old file too. Decay prices value-at-purchase-time, not the good. Fine, but say that; the current text argues from "a genuine difference in the good", which is the argument it just rejected.

**Fix.** Keep decay. Drop the word "anchor". Replace `estimatedCostUsd` as a *cap* with `estimatedCostUsd` as a *displayed claim* plus a mechanism that makes lies costly: the refund window from PLAN.md §5.3 (buyer rejects within N minutes, rejection increments `peer.rejected`, rejection rate is shown in search results). Add a body-similarity check on publish so republishing costs something. State plainly that the tracker fee `ρ_t` is the only thing preventing free listing spam, and set a listing bond.

### 2.6 No deployment phase, so neither sponsor integration can be demonstrated

**What breaks.** Bazantic's tracks require "Create an x402/MPP Gateway in Bazantic for your project" — a reverse proxy pointed at a *public HTTPS base URL* with a reachable OpenAPI spec [V]; Carpool's own `PLAN.md` §2 records "P5 Bazantic needs P6.1 (public HTTPS URL)". The Swarm plan has seven phases and none of them is hosting, TLS, a domain, an OpenAPI document, or secret custody for a public registry that holds everyone's USDC between epochs. Phase 3's acceptance ("a real paid fetch on Hedera testnet with a HashScan link") is satisfiable from localhost. Phase 7 (dashboard) is listed; deployment is not.

**Fix.** Add Phase 3.5: public registry on the OCI A1 box or Fly (Carpool PLAN U7), `/openapi.json`, `LEDGER_API_KEY`-style auth on `/publish`, rate limits, and the key-custody note.

## 4. Gaps — things the plan does not mention

1. **Abuse.** `POST /publish` is "authenticated" but free. A thousand junk artifacts cost the attacker nothing and cost the tracker an embedding call and storage each. Self-purchase: an author buying their own artifact pays price `p` and receives `ρ_a` back — net cost `p − ρ_a` (the tracker's cut) to add a sale to their "health". Nothing detects `buyer == author` or buyer-cluster patterns. World was dropped as friction; nothing replaced it. Minimum: a listing bond refunded on first genuine sale, per-author publish rate limits, and `buyer <> author` excluded from health.
2. **Refund window / disputes.** PLAN.md §5.3 has it; `purchase.refunded` is a column with no code path, no time window, no royalty hold-back. Royalties accrue at purchase and settle within one epoch (Carpool's `EPOCH_SECONDS=600`), so a later refund is unfunded — the same defect Carpool logged as (F).
3. **Storage.** Bodies are MB-sized, stored by the registry ("stores body"). Who pays? R2 is $0.015/GB-mo with free egress [V]; cheap, but unbudgeted and un-designed: no max body size, no quota per author, no retention when an artifact is delisted, no answer to "the author asks for deletion" (§8a says delisting cannot recall copies — correct — but says nothing about the registry's own copy).
4. **Search-query privacy.** The tracker sees every question every user asks *before* they research it — strategy, clients, deals — and forwards each one to a third-party embedding API. This is more sensitive than the artifacts, which at least passed a consent gate. No retention policy, no logging policy, no on-device embedding option, no mention.
5. **Buyer key custody.** `swarm_fetch` pays, so the MCP server holds a Hedera ECDSA private key and a USDC balance on the user's machine, configured in plaintext MCP config. Carpool's fleet uses `maxAmountPerPayment` spend controls (`apps/fleet/src/agent.ts:24`); the plan does not mention spend caps, per-session budgets, or how a user funds the account (Circle testnet faucet, 20 USDC/2 h [HANDOFF]).
6. **MCP output limits.** Claude Code caps MCP tool results at 25,000 tokens by default and spills larger results to a file [V]. A 200 KB research body is ~50k tokens. `swarm_fetch` as designed either truncates, spills, or must chunk/summarise — and the "token saving measured" in Phase 6's acceptance must count the tokens spent *reading* the bought body, which for long artifacts may exceed a focused re-research.
7. **Copyright / quote length.** PLAN.md §8 raises it; the implementation drops it. Selling syntheses of paywalled or ToS-restricted sources is a real exposure and the body carries no quote-length check.
8. **Author signature verification.** `author_sig` is "over manifest_hash (Hedera key)". `author` is an *account id*, not a public key. Verifying needs a mirror-node lookup of the account's current key; keys rotate; multi-sig accounts exist. `AuthorIdentity.verify` (§9) has no key-resolution story.
9. **Dead artifacts and the freshness filter.** §4.2 drops artifacts with `freshness < 0.15` from search, "delisted". But they remain purchasable by magnet at `floor`. Who buys at floor without search? And a 3-half-life-old artifact whose author set `halfLifeDays = 3650` never leaves. `half_life_days` is unbounded in the schema.
10. **Centralisation.** One operator runs the tracker, the embedder, the storage, the escrow account and the settler. The blockchain settles payouts; everything that matters (who ranks first, whose money sits where for ten minutes, what the anchor asserts) is one process. Not disqualifying for v1; unstated.
11. **Operational.** No rate limiting, no `/health`, no reconcile-on-restart for Swarm's ledger (Carpool's `reconcilePending` queries the mirror node network-wide, PLAN (audit) notes it), no backup for the only copy of every body.
12. **Git hygiene.** "Each [phase] ends with… a git tag." `docs/` is currently untracked (`?? docs/`), and the repo's `.gitignore` history shows sqlite/WAL files were once committed — the Swarm registry's `data/` must be ignored from the start.

## 5. What is actually good

- **The pricing decision itself.** PIVOT §1 correctly identifies that Carpool's refund mechanic encodes "split a shared bill" and that Swarm has no shared bill. Rejecting `P/n` here is right, and rejecting buyer-to-buyer refunds for a static good is right. Keeping decay is right. The earlier PLAN.md §6 ("The Carpool split applies unchanged") was wrong and the pivot analysis caught it.
- **Free search, paid body.** §4.2's insistence that the manifest is free is the correct answer to the lemons problem the product faces, and the plan is right that charging for search would kill it.
- **Two ledgers.** "Do not force one schema to serve both" (§2) is correct. Carpool's ledger is `lineage/consumer/accrual` with rebate semantics baked into `addRider`; sharing it would import every Carpool defect ((F), (G)) into Swarm.
- **Quote binding is correctly retained.** The plan sees that a time-varying price plus the facilitator's strict-equality check reproduces exactly the bug `quotebinding.test.ts` exists for. Most people would have missed that.
- **The go/no-go framing.** Writing "collision <10% → stop, write up the negative result" is the right posture even though the measurement is wrong. PIVOT §4's refusal to build Swarm in 48 hours is right and is what saved the Carpool submission.
- **The inherited payment stack is real.** The ledger DB proves 60 settled x402 payments, a real HTS batch and HCS anchors on testnet. `X402-RESEARCH.md`'s pinned facts (package subpaths, `wrapFetchWithPayment` not looping, feePayer id) are genuinely hard-won and will save days.
- **The ENS seam** (§9) is cheap and correctly scoped — one interface, two implementations, `author` opaque. Only fix: the interface needs `payout(): string` separate from `id()`, otherwise "royalty payout resolves through AuthorIdentity, not directly from author" is not actually possible.
- **Torrent vocabulary** is the right UI metaphor and the decay bar is the right thing to spend design effort on.

## 6. Revised recommendation

1. **Fix Phase 0 before running it.** Replace the single-user corpus with (a) a cross-user question set — ask 5–10 people in the ETHOnline/Claude Code community for 20 redacted research questions each, question text only — and (b) a public proxy with ground-truth duplicates. Sample pairs uniformly for the collision rate; enrich near-misses only for the threshold sweep. Derive the P@1 bar from the margin (`m/(1+m)`) and say so. Never commit the corpus; commit the numbers. Budget three days, not one.
